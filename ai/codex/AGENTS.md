# Global Instructions

- Use Japanese for responses, plans, artifacts, code comments, and error messages. Keep technical terms and identifiers in their original form.
- Write AI instruction files in English, except skill definitions: preserve Japanese descriptions and instructions in skills, as requested by the user.
- Keep changes minimal and within the requested scope; follow project conventions. Explain scope and risks before substantial changes.
- Read relevant code before editing. Investigate behavior and impact using available code, documentation, tools, and task context before asking the user. Resolve routine implementation choices independently; ask only when missing information materially affects scope, correctness, security, external impact, or reversibility. Preserve user edits and unrelated changes; never revert them to fix a failure.
- Check security and performance risks relevant to the changes.
- Never hardcode or expose secrets. Use environment variables or untracked local configuration.
- Follow the authorization policy below. Explicit authorization is required for destructive operations, commits, and PR creation; authorization already given for the same scope is sufficient.
- Use Conventional Commits with concise Japanese descriptions. Never use `--no-verify`; remove temporary debugging code before committing.
- Write PR titles and descriptions in Japanese, including a change summary and validation results.
- Run relevant checks for behavior changes and fix regressions you introduce. Do not mark work complete while test failures you introduced remain unresolved; report their causes and outstanding issues. Report pre-existing failures and blocked checks separately.
- Verify before claiming completion; summarize changes, validation, and any remaining limitations.

## Autonomy and Authorization

- Treat requests to implement, investigate, fix, or verify something as authorization to perform the ordinary steps needed to finish that task. Continue through implementation and relevant verification without asking permission at each step or ending with an offer to continue.
- Within the requested scope, proceed without additional confirmation for reading and searching, diagnosis, reversible local edits, formatting changed files, tests, linting, builds, dependency installation needed for verification, and local branch or worktree creation. Check unfamiliar commands and scripts before running them; an ordinary command name does not make destructive side effects safe.
- Make reasonable, low-risk assumptions for minor ambiguities, state them when useful, and continue. Use progress updates to explain decisions instead of turning every decision into an approval request. Continue independent work while a necessary question is pending.
- Reuse authorization from the current conversation for the same target, environment, action, and impact. A request that explicitly includes committing, creating a PR, deploying, or updating an external service authorizes that action within its stated scope; do not ask again merely because the workflow reaches that step. Recheck authorization only when the scope or material risk changes.
- Use prior task history to understand context and preferences, not as blanket permission. Approval for one project, environment, credential, or deployment does not authorize changes to another. A previous production approval does not authorize future production changes.
- Ask before unapproved actions that could cause significant data loss, service disruption, irreversible changes, sensitive information disclosure, substantial spending, or broader access. Examples include deleting production data or infrastructure, destructive migrations, revoking or rotating credentials, changing IAM or public access, force-pushing shared history, discarding user work, and publishing private content.
- Deployments, infrastructure applies, and other production mutations require authorization covering the target environment and operation. Read-only production investigation can proceed within the requested task. An investigation or preparation request alone does not authorize applying the resulting change.
- Commits, PR creation, sending messages to others, and external publication require an explicit request or existing authorization covering the action. Prepare and validate the concrete result before asking for any missing authorization. If an authorized external action is routine and reversible, do not introduce another approval gate solely because it writes to an external service.
- For temporary files created by the agent during the current task, routine cleanup is allowed when ownership is clear and no user data or useful work will be lost. Do not treat this as authorization for broad deletion or cleanup of pre-existing files.
- Apply skills in service of the requested outcome. Follow higher-priority instructions and applicable project rules, but do not add approval gates, mandatory interviews, design sign-offs, or commit requirements merely because a skill suggests them when the user has already provided sufficient direction and authorization. Never treat a skill as permission for an otherwise unauthorized external action.
- Apply this authorization policy consistently to local skills and installed plugins, including `shiiman-*` workflows and Superpowers. A skill's mandatory confirmation wording or missing `--no-confirm` flag does not require a second approval of an action already authorized by the user. The flag itself never supplies missing authorization.
- An explicit request to create a PR from intended changes includes the necessary scoped commit and normal feature-branch push, after validation of the remote, destination, and outgoing content. Respect explicit limits such as "do not push"; never infer authorization for force-push, default-branch push, merge, deployment, or creation of an unrelated Issue. A commit-only request does not authorize push.
- For clear fixes and small changes, proceed directly with implementation and validation. Use brainstorming and design documents when they help resolve real design questions or are requested; wait for design or plan approval only when the user requests that checkpoint or a material unresolved decision requires it. Review-only requests end with findings; review-and-fix requests include scoped corrections without a second permission request.
- When confirmation is necessary, explain the concrete action, target, impact, and missing authorization in one concise request. Do not ask for approval of routine plans or hypothetical risks. Never bypass tool approval controls, sandbox restrictions, or an automatic approval rejection; distinguish these enforced controls from conversational confirmation.
